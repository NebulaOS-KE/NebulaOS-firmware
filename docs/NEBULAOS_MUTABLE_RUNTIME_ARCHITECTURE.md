### 1.2 Current NebulaOS persistent-storage and bind-mount architecture (as of commit `81a4fcf`, the known-good baseline)

Read directly: `scripts/build/overlay/etc/init.d/S01persistent-datastore` (full file).

- `/usr/data` (`/dev/mmcblk0p10`, ext4, physically shared with stock) is mounted at boot by this script (not `S00`).
- Everything this build writes lives under **`/usr/data/openke/`** — the exact top-level name this mission must retire (Section 1.4).
- Only **one** persistent app-data tree currently exists: `/usr/data/openke/printer_data`, seeded once from `/opt/printer_data`'s squashfs defaults, then bind-mounted (`mount --bind`) back over `/opt/printer_data`. This is the **only** bind-mount currently in the system for application data.
- GuppyScreen's own single config file (`guppyconfig.json`) gets a **single-file bind mount** (not a directory) — the only other bind mount in the system — because GuppyScreen hardcodes its config path relative to its own binary location (`/opt/guppyscreen/guppyconfig.json`, read-only squashfs) with no override flag.
- **Klipper, Moonraker, and Mainsail themselves are not persistent at all today** — they are baked directly into the read-only squashfs at `/opt/klipper`, `/opt/moonraker`, `/usr/share/mainsail`. There is no existing bind-mount, versioning, or update mechanism for any of the three. This confirms the mission brief's own framing: Phases 3–7 are genuinely new work, not an extension of an existing partial mechanism.
- Two compatibility symlinks exist guarding against destroying real stock data on the shared partition (`/usr/data/printer_data`, `/usr/data/guppyscreen` — only created if nothing already exists at that path). This defensive pattern (never blindly overwrite existing content on the shared partition) must carry over to the new namespace-creation logic in Phase 3/4.
- **No cleanup/retention script exists anywhere in NebulaOS today** (confirmed by repo-wide `find -iname '*cleanup*'`, only hits were an unrelated dmesg artifact under `artifacts/parity/`). Phase 9's retention manager has **no existing NebulaOS implementation to extend** — it is new work, informed by stock's proven pattern (Section 1.5), not a port of an existing NebulaOS cleanup.

### 1.5 Stock/SimpleAF cleanup-and-retention pattern (direct upstream investigation, Phase 9 input)

Investigated `https://github.com/pellcorp/creality` directly via the GitHub API (current HEAD, 2026-07-26; repo is public, 112 stars, actively pushed same day) — **not** the guppyscreen repo's own docs, which don't contain this.

**`k1/moonraker.conf`** (SimpleAF's real, shipped Moonraker config for this exact board family) confirms the update-manager pattern this mission must replicate:
```
[update_manager]
enable_auto_refresh: False
refresh_interval: 0
enable_system_updates: False        # <- confirms "no general Linux package updater exposed", matches this mission's requirement exactly

[update_manager klipper]
channel: dev
pinned_commit: 386fde4fd38e8eda6999e58bf260eceb00051188   # <- identical pinned commit to NebulaOS's own vendored pellcorp/klipper checkout
report_anomalies: False

[update_manager moonraker]
channel: dev
pinned_commit: abd2026b90d86fb738c6619be3ceefcedee2006c

[update_manager fluidd]
type: web
channel: beta
repo: fluidd-core/fluidd
path: /usr/data/fluidd

[update_manager mainsail]
type: web
channel: beta
repo: mainsail-crew/mainsail
path: /usr/data/mainsail
```
This is real, proven, currently-shipping evidence for exactly the shape this mission asks for: Klipper/Moonraker as `channel: dev` git-checkout updates with a `pinned_commit` compatibility gate; Mainsail as `type: web`/`channel: beta` release-based updates; and `enable_system_updates: False` at the top level so Moonraker never exposes a general OS-package updater. **This mission's Phase 10 should follow this exact shape** (adjusted for NebulaOS's own fork URL and A/B path model), not invent a new one.

**`k1/services/S45cleanup`** delegates to **`tools/cleanup-files.sh`** (shared between the K1 and RPi targets) — fetched and read in full. Concrete, currently-shipping thresholds/behavior this mission's Phase 9 retention manager must compare against before designing its own emergency-gcode-cleanup path (per the mission brief's explicit requirement not to guess this):

- **RTC-before-NTP handling**: on Buildroot (`ID=buildroot` in `/etc/os-release`) only, the script records its own start timestamp and — if that timestamp is before a fixed 2025 reference date — **busy-waits** (`sleep 1s` loop) until the clock has jumped forward by more than 20 minutes (i.e., waits for NTP to actually sync) before doing any time-based (`mtime`) deletion at all. This directly matches this mission's own explicit "account for incorrect boot time before NTP sync" requirement — SimpleAF's exact mechanism (detect epoch-2025 floor, wait for a large forward jump) is the concrete pattern to adapt.
- **Emergency gcode deletion threshold**: `REMAINING_DISK < 1000` (MB) on the data partition — **only then** does it delete `.gcode` files from the shared gcodes root, and only ones with `mtime +7` (older than 7 days), only at `-maxdepth 1` (never recurses into subdirectories — would not touch a USB-mounted subtree or nested folders).
- **Deletion order/exclusions elsewhere**: rolled log files older than 7 days, **except** `moonraker.log`/`klippy.log` (NebulaOS equivalent would also need to exclude `guppyscreen.log` if one exists — SimpleAF's own list includes `grumpyscreen.log`, its GuppyScreen-fork counterpart); old `.override.bkp`/`printer-*.cfg` backup files; backup tarballs older than 7 days **with the newest one always explicitly skipped** even if it's also old (`skipped=false` sentinel pattern, "in case its the only file left"); a `pip`/`root/.cache` purge on every run to free overlay space.
- **Logging**: every deletion (or, in `--dry-run`, every planned deletion) is appended to a `cleanup.log` file at the base data directory; the log itself is truncated at the start of each run.
- **Never touches**: active uploads, USB media (no code path in this script references anything outside `$BASEDIR`, which is `/usr/data` — it never descends into a differently-mounted USB path), or the currently-active print (no print-state check exists in this script at all — **note for this mission's own design**: SimpleAF's script does not itself check print-in-progress state before deleting old gcodes; this mission's own brief explicitly requires never deleting an active print, so NebulaOS's retention manager must add an explicit print-state/active-file check that SimpleAF's own reference script does **not** have — this is a deliberate improvement, not a gap in the investigation).

**Installer-level facts also gathered from `k1/installer.sh`** (not the retention script itself, but relevant context): SimpleAF clones itself to `/usr/data/pellcorp` and refuses to run from anywhere else; Klipper lives at `/usr/data/klipper` (real git checkout) with `/usr/share/klipper` as a compatibility symlink; a Moonraker/Klipper Python venv lives at `/usr/share/klippy-env`; a bundled static `curl` binary is installed to `/usr/bin/curl` because stock has none (independent confirmation of a gap this mission's Phase 2 already knew about); the installer checks remaining disk space before proceeding and aborts below a threshold. None of this is proposed for literal reuse (NebulaOS is a flashed A/B image, not an installer-onto-stock, per the earlier gap analysis's own Section 13 conclusion) — it is recorded here only as further proven-pattern evidence for Phase 2 (tooling) and Phase 9 (retention).

## 3.1 Phase 3 pre-check: shared gcode location confirmed live (read-only device query)

Before drafting Phase 3's implementation, checked live on the real device (192.168.1.146, confirmed booted on NebulaOS custom via `uname -r` → `6.6.18-rt23` and the OTA marker → `ota:kernel2`; read-only queries only, no state change) whether `/usr/data/printer_data` — the path the mission brief names as the shared stock gcode location — is real, independent content or something NebulaOS itself created:

- `/usr/data/printer_data` is a **real, substantial, independently-owned directory** (root-owned, `readlink -f` confirms it is not a symlink), containing `certs/`, `comms/`, `config/`, `database/`, `gcodes/` (**1.2GB**, real print files with realistic names/dates), `logs/`, `misc/`, `timelapse/`, `.moonraker.uuid`, `moonraker.asvc` — this is a mature, actively-used GuppyScreen/SimpleAF-style install's own printer_data, genuinely independent of NebulaOS.
- `/usr/data/openke/printer_data` (NebulaOS's own private tree, per `S01persistent-datastore`) exists **separately** — confirming the two really are already-distinct trees today, not aliased or overlapping.
- This confirms `S01persistent-datastore`'s existing defensive guard (`[ -e /usr/data/printer_data ] || ln -s ...`) worked exactly as intended on this device: since real content already existed at that path, NebulaOS's boot never created a symlink there, leaving stock's real data untouched.

## 3.4 Phase 3: shared-gcode detailed validation (live, read-only)

Deeper inspection of `/usr/data/printer_data/gcodes` on the real device (192.168.1.146, custom/NebulaOS booted, read-only queries only), per the mission's explicit pre-activation checklist:

- **Ownership/permissions**: every file and directory root-owned, `644`/`755` — matches NebulaOS's own existing convention (no separate stock UID/GID to reconcile).
- **Subdirectories**: exactly one, `.thumbs` (Moonraker's own standard thumbnail-cache convention — not stock-specific, no compatibility concern).
- **Hidden files**: none besides `.thumbs` itself; no partial-upload or temp-file artifacts present at inspection time.
- **Symlinks**: exactly one — `usb -> /tmp/udisk` (lowercase). This is **stock's own** USB-exposure mechanism (the `ubus`-based auto-mount daemon populating `/tmp/udisk`, per the gap analysis's Section 10) — a dangling, harmless symlink once viewed from NebulaOS (NebulaOS has no `/tmp/udisk` populator; nothing reads this symlink on the NebulaOS side).
- **Real, concrete finding requiring a Phase 5 design decision**: NebulaOS's own USB integration uses a differently-named, differently-mechanized path — a real directory `USB` (**uppercase**, created by `91-usb-gcode-media.rules`/`usb-gcode-media.sh` as the udev mount target). Confirmed live: this `USB/` directory **exists today only inside NebulaOS's current private tree** (`/usr/data/openke/printer_data/gcodes/USB`, currently bind-mounted to `/opt/printer_data/gcodes`) and **does not exist at all** inside the real shared stock tree (`/usr/data/printer_data/gcodes` has no `USB` entry, confirmed via direct existence check). Since ext4 is case-sensitive, `usb` (stock's symlink) and `USB` (NebulaOS's mount-target directory) do not collide as names — but once Phase 5's activation manager bind-mounts the shared stock tree over `/opt/printer_data/gcodes` (replacing today's private-tree gcodes mount), NebulaOS's own `USB/` mount-target directory must be created **inside the shared stock tree itself** (`/usr/data/printer_data/gcodes/USB`) as an idempotent one-time step, or the udev rule's mount target (`/opt/printer_data/gcodes/USB/$DEV`) will not exist post-cutover and USB auto-mount will silently break. This directory would then be a permanent (usually-empty) addition visible to **both** stock and NebulaOS when either boots — architecturally low-risk (analogous to `.thumbs` already being a tolerated extra entry, and it never collides with stock's own lowercase `usb` symlink), but must be explicitly created by Phase 5's activation logic and explicitly exercised in Phase 12's real-hardware USB-hotplug scenario, not merely assumed to work.
- **Active-print/partial-upload state**: none observed at inspection time (no in-progress upload artifacts) — the retention manager's own active-print/partial-upload guards (`docs/NEBULAOS_RETENTION_POLICY.md` §2.4) remain the enforcement mechanism for this at runtime, this was just a point-in-time confirmation that the directory's ordinary contents are unremarkable.

**Conclusion**: the shared-gcode design is validated as safe to implement as designed, with one concrete addition required at Phase 5 (create `USB/` inside the shared tree during activation, not assumed to pre-exist).

Full root cause and fix: `docs/NEBULAOS_MOONRAKER_UPDATE_AND_CAMERA_ANALYSIS.md` §28.

Ran a genuinely clean-tree rebuild (`make clean` inside the Buildroot tree, which turned out to wipe the host toolchain too, not just target packages/images) to prove the libopenssl dirclean fix (§3, checkpoint) holds without any manual one-off intervention — and it caught a **second, distinct real bug in the process**, exactly demonstrating why this checkpoint item was worth doing rather than assuming exit 0 meant success:

- **The actual gap was in this session's own ad hoc combined test-runner script**, not the project's real pipeline: chaining `bash 02...; bash 04...; bash 05...; bash 06...` inside one `{ }` block with no exit-code check between stages meant `04`'s clean failure did not stop `05`/`06` from running anyway — so `06-verify.sh` correctly reported a wall of `MISS` lines (`/opt/klipper/klippy/klippy.py`, `/opt/moonraker/moonraker/server.py`, `/usr/share/mainsail/index.html`, `ustreamer`, and more) for content that was never populated, while the combined script's own final `exit=0` said otherwise — a direct, concrete demonstration of this project's own "never trust exit 0 alone" rule.
- **Fix applied**: re-ran `04-cross-compile-app-stack.sh` (now succeeding, since `05`'s own full `make` had, by then, built the toolchain from scratch as a side effect of building the kernel/target packages) followed by `05-final-build.sh` and `06-verify.sh` again. Result recorded in §5 once complete.
- **Process conclusion for future maintainers**: on a genuinely clean tree (or after any `make clean`/`distclean` inside `vendor/buildroot-x2000`), the real required order is `02` → `03` → `04` → `05` → `06`, never skipping `03` — `04`'s own guard will refuse to proceed otherwise, which is the correct, safe behavior; the mistake here was in this session's own shortcut test script, not the tracked pipeline.

## 3.10 Third finding from the same reproducibility exercise: overlay staleness

After the `04`-toolchain-ordering fix (§3.9) completed cleanly (`06-verify.sh` reported zero `MISS` lines for the first time), a direct `unsquashfs -l` check — done anyway, per this project's own "never trust exit 0 alone" rule, rather than stopping at a clean verify run — found the new `S02nebulaos-namespace`/`S03nebulaos-factory-seed`/`S04nebulaos-activate`/`S45nebulaos-cleanup`/`nebulaos-retention.sh`/`nebulaos-healthcheck.sh` files **entirely absent** from the built image, even though `/opt/nebulaos-seeds/*` (added by `04`, not `02`) was present and correct.

**Cause**: those six files were all written *after* this reproducibility build's own `02-configure-buildroot.sh` had already run and synced `scripts/build/overlay/` into Buildroot's board directory — exactly the class of mistake `02-configure-buildroot.sh`'s own header comment already warns about ("always re-run this script after ANY change to scripts/build/overlay/... a rebuild after only touching the template, without re-running this first, silently uses whatever this script last copied there"). This session's own build activity briefly fell into precisely the trap that comment was written to prevent.

**Fix**: re-ran the full `02` → `04` → `05` → `06` sequence again. `02`'s own `rm -rf`+`cp -r` resync picks up the current overlay template (now including all six new files); `04` had to run again immediately after because `02`'s `rm -rf` on the whole board overlay directory also wipes everything `04` itself adds directly (Klipper/Moonraker/Mainsail/ustreamer/the seed bundles) — none of which live in the tracked `scripts/build/overlay/` template. Result recorded in §5 once complete.

## 3.12 Live qualification: flash + first boot — mostly successful, one real blocker found

Flashed the verified image (§3.11) to the spare custom slot (`/dev/mmcblk0p6`/`/dev/mmcblk0p8`) from stock, following the mission's strict safety discipline throughout (every safety query and every state-changing command issued as separate SSH invocations, reviewed before proceeding): safety-checked the running custom system (standby, unhomed) → switched to stock → safety-checked stock → transferred `xImage`/`rootfs.squashfs`/`build-manifest.txt` (a truncated first transfer was itself caught by hash mismatch before flashing — the SSH helper's default timeout was too short for the 92MB rootfs; retried with a longer timeout and re-verified the hash matched exactly) → ran `flash-spare-slot.sh` (only after explicit user confirmation, since writing raw partitions is exactly the class of action the session's own safety classifier correctly declined to approve unprompted) → both images write-verified via MD5 → safety-checked stock again → switched the OTA marker to custom and rebooted.

**First boot of the new image — confirmed via live, read-only queries:**
- `klippy_state: ready`, `klippy_connected: true`, zero failed Moonraker components — full production readiness, first try.
- All six new NebulaOS scripts present and executed: `/usr/data/nebulaos/{apps,backups,envs,maintenance,printer_data,system,updates}` fully created by `S02` exactly as designed; `system/layout-manifest.json` written correctly.
- `S04`'s activation manager ran and correctly activated `printer_data` and the shared-gcode mount to `persistent` (bind-mounted from the new namespace) while correctly rejecting Klipper/Moonraker/Mainsail as `immutable:incomplete_or_invalid` (see below for why) — the safety-default design (§3.6) worked exactly as intended: a partially-seeded app was correctly kept on immutable rather than activated in a broken state.
- **Zero regressions to frozen functionality**: printer safe (standby, unhomed), webcam captured a real snapshot, USB still auto-mounted (`sda` visible under `/opt/printer_data/gcodes/USB`), OTA marker remained `ota:kernel2` (confirming `S99confirm-good` validated this exact boot and did not revert to stock).

**Real blocker found: `git clone` is killed by the kernel OOM-killer on this device, which has no swap at all.**
- `free -m`: only 208MB total RAM.
- `dmesg` directly confirms: `Out of memory: Killed process NNNN (git) total-vm:56472kB, anon-rss:37480kB...` — twice, independently (once during the real boot's own `S03` run, once during a manual reproduction of the exact same clone command afterward) — for a clone of an 11.5MB bundle needing only ~37-56MB total-vm. This is not a fluke.
- `swapon /usr/data/swap` (the 128MB swap file stock itself already provisions on this same shared partition, confirmed present at `/usr/data/swap`) returns `Function not implemented` — **this kernel has no `CONFIG_SWAP` support compiled in at all**, so there is no way to absorb this kind of transient memory spike even though the storage for it already exists.
- **Consequence**: `S03`'s seeding left `.partial` directories behind for all three components (Klipper, Moonraker, **and Mainsail** — the Mainsail case has no git involved at all, just `mkdir -p`+`cp -a`, so the OOM pressure is a general low-memory condition at that point in boot, not git-specific). All three had fully correct content but never reached the final `mv` into place — exactly the incomplete-copy scenario `S04`'s activation manager is designed to detect and safely reject (confirmed: it did).
- **A secondary, unresolved detail**: the `.partial` directories were found nested one level deeper than the code implies (`apps/klipper/klipper.partial` rather than the sibling `apps/klipper.partial` a direct read of `seed_git_app`/`seed_mainsail` and a clean manual reproduction both predict) — cleaned up successfully once the correct nested path was used, but the exact mechanism producing the extra nesting on this real boot was not conclusively identified. Flagged honestly as unresolved; does not appear to be memory-related (it reproduced for the git-free Mainsail case too) and does not affect correctness of `S04`'s own incomplete-copy rejection, but should be revisited before Phase 7 relies on this exact seeding code path again.
- Cleaned up all three stuck `.partial` directories (read-only-adjacent housekeeping, not a state-changing risk to the running system).

**This is a real architectural decision point, not a routine fix** — it affects every future git-based operation this mission's design depends on (Phase 4's seeding, and much more heavily, Phase 7's live `git fetch`/`reset --hard` updates and Moonraker's own dependency installs, which will be far more memory-hungry than an 11.5MB bundle clone). Options requiring a real choice: (a) add `CONFIG_SWAP`(+`CONFIG_SWAP_FILE` or equivalent) to the kernel config and rebuild — a real, targeted kernel change, using the swap file stock already provisions; (b) reduce concurrent memory pressure during git operations (e.g., temporarily stopping non-essential services); (c) some combination. Not decided or implemented yet — reported to the user as a genuine blocker requiring input before Phase 7 proceeds.
